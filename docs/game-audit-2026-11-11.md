## 2. 확인된 수정 대상

P1은 화면 전체 실패 또는 공개 전 해결할 차단 문제, P2는 규칙·수명·정확성 문제, P3은 안내·문서 일관성 문제다. 준비 중 게임의 P1은 현재 서비스 장애라는 뜻이 아니라 해당 게임의 공개 차단 사유다.

### F01 · P1 · 공통: 게임 모듈 로딩 실패 시 빈 화면

- **증상:** 게임 코드를 가져오지 못하면 허브까지 사라지고 재시도·돌아가기 버튼도 없다.
- **재현:** 독립 브라우저 컨텍스트에서 밥상 대격돌 모듈 요청을 차단한 뒤 게임을 선택했다. `Failed to fetch dynamically imported module` 예외와 빈 `body`를 확인했다.
- **원인:** [App.tsx:27](../src/App.tsx#L27)에 `Suspense`는 있지만 오류를 처리하는 경계가 없다. Suspense의 로딩 UI만으로 import 실패나 하위 렌더 오류는 복구되지 않는다.
- **수정:** 게임 단위 Error Boundary, 허브 복귀, 재시도 안내. 청크 갱신 실패는 새로고침 복구 경로를 구분하고 저장 데이터는 보존한다.
- **검증 기준:** 요청 실패·렌더 예외를 주입해도 허브 복귀가 가능하고 다른 게임을 실행할 수 있어야 한다.
- **증거:** [실패 화면](../output/playwright/audit-2026-11-11/chunk-failure.png), [예외](../output/playwright/audit-2026-11-11/chunk-failure.json).

### F02 · P1 · 삼국지 패업 PK: 손상 저장본을 정상으로 판정

- **증상:** 필수 데이터가 빠진 저장본으로 이어하기를 선택하면 빈 화면이 된다.
- **재현:** 정상 `createGameState('caocao')` 결과에서 `units`만 제거해 저장했다. `loadGame()`이 이를 반환했고, 허브의 이어하기 클릭 후 `Cannot convert undefined or null to object`가 발생했다.
- **원인:** [save.ts:40](../src/games/three-kingdoms/game/save.ts#L40)의 검증은 지도 크기·도시·장수·플레이어 세력 일부에 국한된다. `units`, 명령, 로그, 개체 참조 무결성 등은 확인하지 않는다.
- **수정:** 저장 스키마와 관계 검증을 추가하고, 잘못된 기록은 원본 보관·내려받기·새 게임 선택으로 복구한다. 기존 버전의 정상 기록은 마이그레이션 후 검증한다.
- **검증 기준:** 필드 누락·잘못된 세력/장수/부대 참조를 거부하고 정상 구버전 기록은 복구해야 한다.
- **증거:** [실패 화면](../output/playwright/audit-2026-11-11/pk-corrupt-save.png), [예외](../output/playwright/audit-2026-11-11/pk-corrupt-save.json).

### F03 · P2 · 밥상 대격돌: 같은 프레임 공격에 1P 처리 우선권

- **재현:** 같은 주걱, 서로 100 거리, `fight` 상태에서 양쪽에 동시에 `jab`을 입력하고 0.05초씩 두 번 진행했다. 결과는 **1P HP 100 / 2P HP 94**, 2P 공격 취소였다.
- **원인:** [engine.ts:93](../src/games/kitchen-fighter/engine.ts#L93)에서 선수별 업데이트와 피격 적용을 순서대로 수행한다. 먼저 계산한 1P가 [상대 공격을 취소](../src/games/kitchen-fighter/engine.ts#L127)해 2P의 같은 시점 공격이 사라진다.
- **수정:** 프레임 시작 상태를 기준으로 양쪽 판정을 수집한 뒤 함께 적용한다. 상쇄·동시 피격·우선순위 규칙을 명시한다.
- **검증 기준:** 선수 인덱스를 바꿔도 대칭 상황의 결과가 같아야 한다. 무기별 발동 속도 차이에 따른 선공은 유지한다.

### F04 · P2 · 밥상 대격돌: WebGL 실패 후 시작하면 안내도 사라지고 멈춤

- **재현:** WebGL 컨텍스트 생성을 실패시켰다. 선수 선택에서는 오류 안내가 나왔지만 시작 버튼은 활성화돼 있었다. 시작 후 오류 문구는 사라지고 `ROUND 1 준비!`에서 진행하지 않았다.
- **원인:** [KitchenFighterApp.tsx:95](../src/games/kitchen-fighter/KitchenFighterApp.tsx#L95)의 생성 실패가 렌더 루프를 종료한다. 오류는 설정 화면에서만 표시하고 시작 버튼은 이미지 로딩 여부만 본다.
- **수정:** 렌더러 준비 상태로 시작을 제어하고, 경기 화면에서도 오류·복귀를 제공한다. 지원 가능한 2D 대체 화면은 별도 선택 사항이다.
- **증거:** [실패 화면](../output/playwright/audit-2026-11-11/kitchen-no-webgl.png).

### F05 · 공개 차단 P1 · 색깔 맞추기: 정지·재개마다 실행 루프 누적

- **재현:** rAF 대기열을 계측했다. 시작 직후 1개 → 정지/재개 3회 후 **4개**. `destroy()` 후에도 **3개**가 남았다.

- **수정:** 단일 루프 소유권과 상태 가드를 두고 정지·종료·파괴 시 예약을 해제한다. 반복 정지/재개 및 종료 후 0개 콜백을 검증한다.

## 4. 플랫폼 공통 개선

1. **저장 API 통합:** 읽기/쓰기 성공 여부, 스키마 버전, 저장 시각, 복구 가능한 원본을 공통 계약으로 둔다. 장기 전략/RPG는 백업·복구를 먼저 적용하고 짧은 아케이드는 최고 기록만 관리한다.
2. **실행 수명 계약:** 엔진의 `start/pause/resume/destroy`를 통일하고 중복 호출에 안전하게 만든다. rAF·타이머·키/포인터·오디오·ResizeObserver를 세션이 소유하도록 정리한다.
3. **입력과 모달:** 각 게임의 다른 일시정지 표기를 정리하고, 포커스가 모달 밖으로 나가지 않는지 검증한다. 특히 밥상 대격돌은 자체 오버레이에 명시적인 dialog/focus 관리가 필요하다.
4. **브라우저 이동:** 현재 활성 게임은 React 상태에만 있다. 게임 URL/뒤로가기/새로고침 정책을 정하면 게임 공유와 재접속이 쉬워진다. 진행 저장과 URL 상태는 별도로 취급한다.
5. **성능 측정:** Vite 경고의 Three.js 579KB 청크만 보고 재구성하지 않는다. 첫 허브/게임 첫 로딩량, 프레임 시간, 반복 게임 교체 후 메모리·WebGL 컨텍스트 수를 먼저 측정한다. GPU 그림자와 픽셀 비율은 기기별 품질 옵션 후보다.
6. **회귀 검증:** 지금 322개 중 일부 UI 검사는 HTML 문자열/정적 렌더 검사다. 실제 브라우저의 로딩 실패, 포커스, 저장 실패, 터치 입력을 대신하지 못한다. 모든 게임에 최소 시작→입력→정지/재개→종료/복귀 스모크를 추가한다.
7. **CI:** 현재 작업 트리에서 `.github` 워크플로는 발견되지 않았다. 별도 외부 CI 여부는 미확인이다. 빌드·규칙 테스트와 소수의 브라우저 스모크를 자동화하면 안정성이 높아진다.

## 5. 별도 `apps/three-kingdoms-web` 검토

- 현재 Vite 허브의 삼국 영지는 **로컬 시뮬레이션**이다. 별도 Next.js 페이지도 `GameDemo` 체험 화면이며 서버 `/api/battle`과 UI가 통합돼 있지 않다. 온라인 전투/계정 저장이 현재 제공된다고 보면 안 된다.
- API 코드의 장점은 Supabase `getUser(token)` 검증, 요청 UUID 스키마, 공격 부대 소유권 검증, Serializable 트랜잭션·재시도, `requestKey` 멱등성이다. 이는 코드 구조 확인이며 실제 DB에서 성립함을 검증한 결과는 아니다.
- 테스트 디렉터리는 있으나 이 작업 환경에는 앱 의존성이 없다. 실행 시 `tsx is not recognized`로 끝났으므로 서버 테스트 통과로 보고하지 않는다.
- 온라인화 전 우선순위: 로컬/서버 전투 규칙 차이 정리 → 계정과 사용자 초기 데이터 생성 → 모집/편성/건설/장비 서버 API → UI 연결 → 실제 PostgreSQL 동시 요청·보상 중복·인증 실패 검증.
- 루트와 앱이 각각 `demoGame`, `battleEngine`, 장수 카탈로그를 갖고 있다. 이미 콘텐츠 범위도 다르므로 공유 순수 규칙 패키지 또는 명시적인 규칙 버전 전략이 필요하다.
- Supabase/DB 운영 상태·자격 증명·RLS 실효성은 이번 점검으로 판정하지 않았다. 기존 DB를 변경하거나 마이그레이션을 실행하지 않았다.

## 6. 권장 실행 순서와 완료 기준

| 순서 | 작업 묶음 | 완료 기준 |

## 7. 재현 자료 사용

엔진 경계 재현은 프로젝트 루트에서 다음 명령으로 다시 실행할 수 있다.

```powershell
node output/playwright/audit-2026-11-11/probes.mjs
```

이 파일은 소스 모듈을 esbuild로 메모리 번들링하고 별도 모의 타이머/저장소를 사용한다. 실제 사용자 기록을 수정하지 않는다. 브라우저 검사도 새 자동화 컨텍스트에서 수행했으며 사용자 브라우저의 기존 저장소는 사용하지 않았다.
